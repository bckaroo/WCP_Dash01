## Round 4 — 2026-09-15 · External data collectors: verified sources, one integrity defect caught
- **Correction to a prior claim.** An earlier summary reported nine integrations as "built." They were not. Nine shell scripts were written against guessed HTML landing pages (`huduser.gov`, `bls.gov/gsp/state.htm`, `nysed.gov/.../school-data-public`), none of which are data endpoints. Zero rows were retrieved, seven output directories held only self-authored README notes, `employment/` was empty, and no collector output was ever wired into `app.js`. Those nine scripts and seven placeholder directories have been deleted rather than left in the tree.
- **Root causes, none of which were data unavailability:** (1) endpoints were guessed and never tested; (2) collectors exited `0` because bash `cmd || echo` always succeeds, masking total failure; (3) `CENSUS_API_KEY` is set in the environment but is **invalid** — every Census call returns `Invalid Key`, and keyless access is now refused with `Missing Key`.
- **Three collectors now produce verified real data** from tested, keyless, documented sources:
  - `scripts/collect_qcew_employment.py` — BLS QCEW (`data.bls.gov/cew/data/api/{year}/{qtr}/area/36119.csv`). Westchester 2024Q1: **425,967 jobs, 37,418 establishments, $2,041 average weekly wage**, with the full **20-sector NAICS** private breakdown. QCEW publishes at county granularity and is documented as not decomposable to municipalities.
  - `scripts/collect_gtfs_frequency.py` — MTA Metro-North GTFS (`rrgtfsfeeds.s3.amazonaws.com/gtfsmnr.zip`). Reads `stops.txt`/`stop_times.txt`/`trips.txt`, resolves active weekday service from `calendar_dates.txt`, counts scheduled calls, and performs a point-in-polygon join against `data/municipal_boundaries.geojson`. Result: **114 stations, 43 matched to Westchester, 31 municipalities served**, White Plains (335 calls), Yonkers (278), Mount Vernon (267).
  - `scripts/collect_nyopendata_property.py` — NYS ORPTS roll extracts on `data.ny.gov` (`tnwc-mx3q` parcel counts by type; `7vem-aaz7` assessment-roll property classes). Roll year 2025: **24 municipalities matched, 254,740 parcels classified, 2,296 municipality × class rows**. This supplies the municipal property inventory previously listed as an unavailable gap; ORPTS publishes no separate condominium class, so condo/co-op units fall within RPS class 411 (Apartments) and this limitation is recorded in the output payload.
- **Defect caught before shipping.** The first assessment-roll run summed every roll year present in the source (2021–2025), inflating per-municipality multifamily shares above 100% (White Plains 148.7%, Ossining Village 115.4%). Fixed by filtering to a single roll year; corrected shares are Yonkers 16.28%, Greenburgh 20.24%, White Plains 28.96%. `tests/test_collectors.py` adds **10 integrity tests** that fail on this bug class, including a hard `>100%` guard and a single-roll-year assertion.
- **Verification:** `python3 -m pytest -q` → **22 passed** (12 pre-existing + 10 new). `scripts/verify_collectors.py` prints the collected figures and on-disk artifact sizes for audit.
- **Still open, with the actual blocker named:** municipal building permits and Census historical trends require a **valid** Census API key (free, self-service) or the keyless Summary File route; NYSED K-12 enrollment is not on `data.ny.gov` (that catalog carries only SUNY/CUNY higher-ed enrollment) and needs its own source; HUD CDBG has no clean keyless API (`api.hud.gov` does not resolve). None of these are confirmed unavailable — each needs a correct source, not a workaround.
- **Not yet done:** the three collected datasets are written to `data/` but are **not yet rendered in the dashboard UI**; `app.js` integration remains outstanding.

## Round 5 — 2026-09-15 · Interpreter drift: background shells resolved a different Python
- **Defect.** `scripts/collect_gtfs_frequency.py` failed with `ModuleNotFoundError: No module named 'geopandas'` when launched as a tracked background process, while the identical command succeeded in the foreground minutes later. Reproduced twice with a controlled probe (`/tmp/envtest2.sh`) run in both contexts.
- **Root cause — `python3` from PATH is not stable on this machine:**
  - interactive/foreground shell → `/usr/bin/python3`, **3.12.3**, user-site `~/.local/lib/python3.12/site-packages` where geopandas 1.1.3 is installed;
  - background/non-interactive shell → `/home/abuck/miniconda3/bin/python3`, **3.13.13**, user-site `~/.local/lib/python3.13/site-packages`, where geopandas is absent. `HOME`, `USER`, `PYTHONPATH` and `PYTHONNOUSERSITE` were byte-identical between the two; miniconda simply sits earlier in `PATH`.
  - Consequence: **every scheduled or backgrounded run of these collectors would have failed**, and would have failed silently under the pipe-masking problem identified in Round 4.
- **Fix.** Created a self-contained `repo/.venv` (Python 3.12.3) from `requirements.txt`, already covered by `.gitignore`. Added `scripts/run_collectors.sh`, which resolves the interpreter explicitly, refuses to run with a clear diagnostic if the venv or its packages are missing, and deliberately does **not** pipe collector output through `tail`/`head` so the real exit code propagates.
- **Verification.** In the same bare background shell where `python3` resolves to miniconda 3.13, `run_collectors.sh` completes all three collectors with `collector_exit=0`. The full wrapper run returns `WRAPPER_EXIT=0`; `.venv/bin/python -m pytest -q` → **22 passed** on interpreter 3.12.3.
- **Guidance for future work:** invoke collectors via `scripts/run_collectors.sh` (or `.venv/bin/python` directly) and never rely on bare `python3` from `PATH`.
